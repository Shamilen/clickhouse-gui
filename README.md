# ClickHouse TTL

Локальное приложение для просмотра TTL, сроков хранения и мутаций ClickHouse. Интерфейс на русском языке.

## Запуск

Нужны Python 3.10 или новее и Tkinter. Проверить наличие Tkinter можно командой `python3 -m tkinter`. На Debian и Ubuntu системный пакет называется `python3-tk`. В Windows используйте `py` вместо `python3`.

Распакуйте архив и запустите из папки с приложением:

```sh
python3 app.py
```

Укажите HTTP(S)-адрес конкретного узла ClickHouse, логин, пароль и базу. Начальное значение базы — `dtracing`. При подключении по сети используйте HTTPS с доверенным сертификатом. Пароль хранится только в памяти процесса. Для просмотра нужны права на соответствующие системные таблицы. Подсчёт строк требует `SELECT` на целевой таблице, а изменение TTL и его материализация требуют соответствующих прав `ALTER`.

## Работа с TTL

1. Подключитесь и выберите таблицу. В списке показаны размер, число строк и наличие TTL таблицы. Полное определение доступно на вкладке **DDL**. В список входят таблицы выбранной базы и известные системные логи, включая копии с числовым суффиксом, если они видны на узле.
2. Откройте **Настроить TTL**, выберите столбец даты и задайте срок хранения от 1 до 3650 дней. Для `tenant` можно добавить исключения по одному на строку, например `sage=3`. Шаблоны заполняют 7 дней по умолчанию и 3 дня для указанных tenant. При целочисленном `spans_v5.start_time` выбирайте вариант Unix-секунд, если столбец действительно хранит секунды.
3. Проверьте SQL. Кнопка подсчёта выполняет `SELECT count()` по условию истечения на всей таблице или в ранее выбранной партиции. Запрос ограничен 25 секундами и 2 ГиБ чтения. При превышении лимита ClickHouse возвращает ошибку. Число совпавших строк относится к моменту подсчёта. Освобождённое место зависит от физических частей и фоновой очистки.
4. Подтвердите **Заменить TTL**. `MODIFY TTL` заменяет все правила TTL таблицы, включая действия переноса или агрегации, если они присутствуют. TTL отдельных столбцов виден в DDL. Для запроса приложение передаёт `materialize_ttl_after_modify=0`, чтобы сам ALTER не ставил задачу материализации исторических частей в очередь. Новый TTL участвует в обычной работе ClickHouse после изменения DDL.
5. На вкладке **Партиции** загрузите активные части, выберите партицию и запустите очистку по сохранённому TTL. Для всех партиций предусмотрена отдельная команда. На вкладке **Мутации** нажмите **Обновить мутации**. Статус принятой команды и её Query ID появляются сразу, физическая обработка выполняется асинхронно. Ошибку конкретной мутации можно увидеть при выборе строки.

## Особенности сервера

- Партиционная очистка использует `ALTER TABLE … MATERIALIZE TTL IN PARTITION ID …`. Команда применяет действующие действия TTL. Настройки `materialize_ttl_recalculate_only` и `ttl_only_drop_parts` влияют на фактическое удаление. Перед отправкой приложение сверяет узел, UUID и DDL таблицы со снимком, показанным в интерфейсе.
- Статистика и выборки показывают тот узел, к которому подключилось приложение. Для кластера учитывайте репликацию таблиц и локальность системных логов. Приложение отправляет DDL без `ON CLUSTER`.
- Постоянную политику активных системных логов задавайте в конфигурации сервера. Для стандартной конфигурации `query_log` это `<query_log><ttl>event_date + INTERVAL 3 DAY</ttl></query_log>`. При заданном `<engine>` добавьте TTL в его выражение. При пересоздании лога старая таблица может остаться с числовым суффиксом.
- `event_date` задаёт календарную границу, связанную с полуночью. Выбирайте `event_time`, если срок должен отсчитываться от времени конкретного события.
- Проверено на ClickHouse 25.8.33.6 с синтетическими данными и HTTP-интерфейсом.
